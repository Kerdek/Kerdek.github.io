Lambda Calculus for Formal Proof

The Verification Gap

If you've spent time writing functional programs, you've experienced a familiar tension. You write a function, test it on inputs, watch it behave correctly, and yet some nagging doubt remains. Does it always work? For every possible input? You may tell a colleague "the result is never negative". That claim transcends any finite test suite. That claim is not about a handful of test cases; it's about all possible inputs—a universal property. Yet, your evidence remains circumstantial.

This gap between testing and certainty has driven programmers toward various solutions: more tests, property-based testing, careful code review, defensive programming, sophisticated typing, and flagging systems. These are valuable practices, but they share a fundamental limitation: they can show the existence of counterexamples, but they don't establish universal truths. Those live in comments, documentation, and natural language discussions. Those are not checked by rigorous machinery.

Herein lies an alternative: what if your claims about programs could be expressed with the same mathematical precision as the programs? What if proving its properties was as sure as checking its types? This is the promise of the Curry-Howard correspondence, the profound connection between programs and proofs that underlies much of modern proof assistants and dependently-typed programming languages.

The Curry-Howard Correspondence

This correspondence establishes a precise mapping between domains that might seem unrelated:

  • Logic: propositions, proofs, and inference rules
  • Programs: types, terms, and typing judgments

By Curry-Howard, each logical construct is a programming construct:

A logical proposition is a type. A proof of that proposition is a term inhabiting that type. To prove a proposition is to provide a well-typed term. Logical implication (P → Q) is a function type P → Q. Universal quantification (∀i.P) is a polymorphic type ∀i.P. Rules of logical inference are typing rules. A type checker is a proof checker. Type soundness is logical soundness.

From Testing to Proving

Consider how we reason about programs. You write a function square that multiplies a number by itself. You might informally claim "square always returns a non-negative result for real number inputs." How do you gain confidence in this claim? You might test: non_negative (square 2), non_negative (square -3), non_negative (square 0). You might reason informally: "Multiplying two numbers of the same sign never gives a negative result, and squaring uses the same number twice...". This reasoning is sound, but it exists only in prose. Each test increases your confidence, but you can never test all real numbers.

Our approach changes this informal reasoning into formal, mechanically-checked mathematical objects. The property is expressed as a proposition.

∀x.real x → non_negative (square x)

You can construct a term of that type, and it is a proof. This proof accepts proof that x is real and returns proof that square x is non_negative. Testing can show the presence of bugs, but never their absence. This proof, by contrast, establishes a universal property for all inputs. You close the gap between specification and implementation: the specification is a type, the correctness is a term, and the type checker ensures it is valid.

Why Lambda Calculus?

We begin from the untyped lambda calculus because it is a simple model of computation. In this system, your programs are unconstrained. You can write square = λx.mul x x without any type annotations. We won't constrain the program with types. We will restrict what counts as proof about those programs. That is, the program will be part of the proposition. The proposition does not add typing to the program, it is a type that expresses the property. We write programs, we make propositions about those programs, and we construct proofs for those propositions.

Propositions about Programs

Propositions are a richer language built from arrows, quantifiers, and parts of programs. We can put a program in a proposition. A program that returns a proposition is a predicate. We augment the syntax with:

  • Arrows →: Implication. P → Q says "P implies Q."
  • Quantifiers ∀: For all. ∀x.P says "For all x, P."

These are features of propositions which state properties. Our programs remain untyped, but they occur in propositions, and those say things about them.

∀x.real x → non_negative (square x) is a proposition. The program square is part of it. Read this as: "For all x, if x is a real number, then x2 is non-negative."

real and non_negative are predicates. The arrow → connects the antecedent to the consequent. The quantifier ∀x. ranges over all possible inputs.

Proofs as Terms

A type might be inhabited by a term (e.g. 2 inhabits Int). A proposition is a type which is proved by its inhabitants—proofs.

To prove ∀x.real x → non_negative (square x), we need a term of this type. This term would look like:

Λx. λP : real x. MulNonNegative x x P P (Refl (sign x))

The type abstraction Λx introduces the type variable x. The abstraction λP : real x introduces a proof of type real x—we're assuming the antecedent. The body proves non_negative (square x).

MulNonNegative is a proof that a real product is non_negative when the coefficients have equal sign. Its proposition is:

∀a b. real a → real b → eq (sign a) (sign b) → non_negative (mul a b)

Refl takes care of eq (sign x) (sign x):

∀a.eq a a

The proof has computational meaning. It takes proof that real x, applies reasoning about multiplication, and produces proof that the result is non_negative.

The system is untyped only with respect to the programs being discussed, but it is very much typed with respect to proofs. The propositions form a typing system that lets you make universal claims about those untyped programs, and the proof terms are just lambda terms whose typing rules mirror logic. That's the move that closes the verification gap: you're not typing your program; you're typing your argument about the program.

Rules of Inference

These are the four possible ways to construct proofs. Each of them uses the context Γ to track types.

Generalization (∀ Introduction)

Logical form: Given arbitrary i, P. So, ∀i.P.

Proof term: Type abstraction which proves ∀i.P:

Λi.E

This is a generalization over given i of proof E : P.

Judgment rule: i must not be bound in Γ, and E must prove P[j := i] in Γ, i (proposition i appended to Γ).

i ∉ Γ

Γ, i ⊢ E : P[j := i]

Γ ⊢ Λi.E : ∀j.P

Mechanics: Λa. discharges the universal quantifier ∀a. in the goal and introduces an arbitrary a in the context. The body uses these like type parameters.

Example:

theorem ImpRefl : ∀a.a → a := Λa. λPa : a. Pa.

The body λPa : a.Pa proves a → a for arbitrary a.

Specialization (∀ Elimination)

Logical form: ∀i.P. So, P[i := T] for arbitrary T.

Proof term: Type application which proves P[i := T].

E Q

This is a specialization of proof E : P for proposition Q.

Judgment rule: Q must be closed in Γ, and E must prove ∀i.P in Γ.

Γ ⊢ Q

Γ ⊢ E : ∀i.P

Γ ⊢ E Q : P[i := Q]

Mechanics: When Pa : ∀i.a → i, Pa (real x) proves a → real x. This instantiates the proof for specific propositions.

Examples:

theorem FalseOfFalse : false → false := ImpRefl false

Conditional Proof (→ Introduction)

Logical form: Assuming premise P, Q. So, P → Q.

Proof term: Lambda abstraction which proves P → Q:

λi : P.E

This is a conditional proof on premise i : P of proof E : Q.

Judgment rule: i must not be bound in Γ, P must be closed in Γ, and E must prove Q in Γ, i : P.

i ∉ Γ

Γ ⊢ P

Γ, i : P ⊢ E : Q

Γ ⊢ λi : P.E : P → Q

Mechanics: λPa : t. discharges the antecedent t → in the goal and introduces a premise Pa : t in the context. The body uses these like function parameters.

Example:

theorem Syllogism : ∀a b.a → (a → b) → b := Λa b. λPa : a. λPab : a → b. Pab Pa.

The body Pab Pa proves b for arbitrary propositions a and b and premises Pa : a and Pab : a → b.

Modus Ponens (→ Elimination)

Logical form: P → Q and P. So, Q.

Proof term: Function application which proves Q:

E F

This is a modus ponens through proof E : P → Q from proof F : P.

Judgment rule: F must prove P, and E must prove P → Q in Γ.

Γ ⊢ F : P

Γ ⊢ E : P → Q

Γ ⊢ E F : Q

Mechanics: When Pab : a → b and Pa : a, Pab Pa proves b. This applies the proof to specific premises.

Summary

This calculus makes proof judgment mechanical: writing a proof is writing a well-typed term. Type soundness guarantees logical soundness. If a proof type-checks, it is a valid proof of its proposition.
