Lambda Calculus for Formal Verification

The Verification Gap

If you've spent time writing functional programs, you've experienced a familiar tension. You write a function, test it on inputs, watch it behave correctly, and yet some nagging doubt remains. Does it always work? For every possible input? You may tell a colleague "the result is never negative". That claim transcends any finite test suite. That claim is not about a handful of test cases; it's about all possible inputs—a universal property. Yet, your evidence remains circumstantial.

This gap between testing and certainty has driven programmers toward various solutions: more tests, property-based testing, careful code review, defensive programming, sophisticated typing, and flagging systems. These are valuable practices, but they share a fundamental limitation: they can show the existence of counterexamples, but they don't establish universal truths. Those live in comments, documentation, and natural language discussions. Those are not checked by rigorous machinery.

Herein lies an alternative: what if your claims about programs could be expressed with the same mathematical precision as the programs? What if proving its properties was as sure as checking its types? This is the promise of the Curry-Howard correspondence, the profound connection between programs and proofs that underlies much of modern proof assistants and dependently-typed programming languages.

The Curry-Howard Correspondence

This correspondence establishes a precise mapping between domains that might seem unrelated:

  • Logic: propositions, proofs, and inference rules
  • Programs: types, terms, and typing judgments

By Curry-Howard, each logical construct is a programming construct:

A logical proposition is a type. A proof of that proposition is a term inhabiting that type. To prove a proposition is to provide a well-typed term. Logical implication (P → Q) is a function type P → Q. Universal quantification (∀a.P) is a polymorphic type ∀a.P. Rules of logical inference are typing rules. A type checker is a proof checker. Type soundness is logical soundness.

Why Lambda Calculus?

Alonzo Church's untyped lambda calculus is a simple model of computation. square = ⅂a.mul a a is a program. It has no type annotations. In this system, programs are not constrained by types.

define square ⅂a. mul a a.

You might claim square always returns a non-negative result for real number inputs. How do you gain confidence in this claim? You might test: non_negative (square 2), non_negative (square -3), non_negative (square 0). Each test increases your confidence, but you can never test all real numbers. You might reason informally: "Multiplying two numbers of the same sign never gives a negative result, and squaring uses the same number twice...". This reasoning is sound, but it is prose.

From Testing to Proving

Testing can show the presence of bugs. Proof, by contrast, establishes a universal property for all inputs. It closes the gap between specification and implementation: the specification is a type, the correctness is a term, and type judgment ensures it is valid.

We won't constrain the program with types. We will constrain what counts as proof about a program. That is, the program will be part of a proposition:

theorem Real-non_negative-square ∀a. Real a → non_negative (square a).

"For all a, if a is a real number, then a2 is non-negative."

The proposition does not add typing to the program. It is a type that expresses the property. There is a term of that type, which is a proof. We write programs, make propositions about those programs, and construct proofs for those propositions.

Propositions about Programs

Propositions are a richer language built from arrows, quantifiers, and parts of programs. We can put a program in a proposition. A program that returns a proposition is a predicate. We augment the syntax with:

  • Arrows →: Implication. P → Q says "P implies Q."
  • Quantifiers ∀: For all. ∀a.P says "For all a, P."

These are features of propositions which state properties. Our programs remain untyped, but they occur in propositions, and those say things about them.

∀a.Real a → non_negative (square a) is a proposition. The program square is part of it.

Real and non_negative are predicates. The arrow → connects the antecedent to the consequent. The quantifier ∀a. ranges over all possible inputs.

Proofs as Terms

A type might be inhabited by a term (e.g. 2 inhabits Int). A proposition is a type which is proved by its inhabitants, proofs.

To prove ∀a.Real a → non_negative (square a), we need a proof (a term) of this proposition (this type). Such a proof is:

proof Real-non_negative-square Ʌa. ⅂pa: Real a. Real-non_negative-mul (a) (a) pa pa [ Eq-refl (sign a)].

The universal proof Ʌa. is a type abstraction which introduces the type variable a. The conditional proof ⅂pa: Real a. is an abstraction which introduces proof pa of Real a, the antecedent. The body proves non_negative (square a), the consequent.

This proof accepts proof that a is Real and returns proof that square a is non_negative.

Real-non_negative-mul is a proof that mul a b is non_negative when a and b are Real and have equal sign. Its proposition is:

theorem Real-non_negative-mul ∀a b. Real a → Real b → Eq (sign a) (sign b) → non_negative (mul a b)

Eq-refl takes care of Eq (sign a) (sign a):

theorem Eq-refl ∀a. Eq a a

The proof has computational meaning. It takes proof of Real a, applies reasoning about multiplication, and produces proof of non_negative (square a).

The system is untyped only with respect to the programs being discussed, but it is very much typed with respect to proofs. The propositions form a typing system which makes universal claims about those untyped programs, and the typing rules of proof terms mirror logic. That's the move that closes the verification gap: you're not typing your program; you're typing your argument about the program.

Summary

This calculus makes proof judgment mechanical: writing a proof is writing a well-typed term. Type soundness guarantees logical soundness. If a proof type-checks, it is a valid proof of its proposition.

Appendices

Meaningful Judgmental Equalities

Propositions may be related by judgmental equalities. Certain judgmental equalities are meaningless because they lead these inference rules to contradiction. For example, in the theory of unintepreted functions, Russell's classic paradox, Y not shows the contradiction.

-- statement of contradiction define False ∀a. a. -- `Not a` means `a` implies `False` define Not ⅂a. a → False. -- fixed point combinator define Y ⅂f. (⅂a.f (a a)) (⅂a.f (a a)). -- Russell's theorem theorem Russell Y Not. proof Russel ⅂pfp: Y Not. pfp pfp. -- inconsistency theorem Contradiction False. proof Contradiction Russell Russell.

There are numerous accounts of meaningful judgmental equalities. Some examples include:

  • Set Theories

Rules of Inference

These are the four possible ways to construct proofs. Each of them uses the context Γ to track types.

Generalization (∀ Introduction)

Logical form: Given arbitrary a, P. So, ∀a.P.

Proof term: Type abstraction which proves ∀a.P:

Ʌb.E

This is a generalization over given b of proof E : P[a := b].

Judgment rule: b must not be bound in Γ, and E must prove P[a := b] in Γ, b (proposition b appended to Γ).

b ∉ Γ

Γ, b ⊢ E : P[a := b]

Γ ⊢ Ʌb.E : ∀a.P

Mechanics: Ʌb. discharges the universal quantifier ∀a. in the goal and introduces an arbitrary b in the context. The body uses these like type parameters.

Example:

theorem Imp-refl ∀a. a → a. proof Imp-refl Ʌa. ⅂pa: a. pa.

The body ⅂pa: a.pa proves a → a for arbitrary a.

Specialization (∀ Elimination)

Logical form: ∀a.P. So, P[a := Q] for some Q.

Proof term: Type application which proves P[a := Q].

E Q

This is a specialization of proof E : P for proposition Q.

Judgment rule: Q must be closed in Γ, and E must prove ∀a.P in Γ.

Γ ⊢ Q

Γ ⊢ E : ∀a.P

Γ ⊢ E Q : P[a := Q]

Mechanics: When pa proves ∀x.x → y, pa (Real a) proves Real a → y. This instantiates the proof for specific propositions.

Examples:

theorem False-of-False False → False. proof False-of-False ImpRefl (False).

Conditional Proof (→ Introduction)

Logical form: Assuming premise P, Q. So, P → Q.

Proof term: Lambda abstraction which proves P → Q:

⅂a: P.E

This is a conditional proof on premise a : P of proof E : Q.

Judgment rule: a must not be bound in Γ, P must be closed in Γ, and E must prove Q in Γ, a : P.

a ∉ Γ

Γ ⊢ P

Γ, a : P ⊢ E : Q

Γ ⊢ ⅂a : P.E : P → Q

Mechanics: ⅂pa: t. discharges the antecedent t → in the goal and introduces a premise pa : t in the context. The body uses these like function parameters.

Example:

theorem Imp-syl ∀a b. a → (a → b) → b. proof Imp-syl Ʌa b. ⅂pa: a. ⅂pab: a → b. pab pa.

The body pab pa proves b for arbitrary propositions a and b and premises pa : a and pab : a → b.

Modus Ponens (→ Elimination)

Logical form: P → Q and P. So, Q.

Proof term: Function application which proves Q:

E A

This is a modus ponens through proof E : P → Q from proof A : P.

Judgment rule: A must prove P, and E must prove P → Q in Γ.

Γ ⊢ A : P

Γ ⊢ E : P → Q

Γ ⊢ E A : Q

Mechanics: When pab : a → b and pa : a, pab pa proves b. This applies the proof to specific premises.
